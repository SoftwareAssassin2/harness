Build the solution for ticket {ticket}, variation {variation} of project {project}.

{where}

1. Read {ticket-folder}/execution-plan-{variation}.md, {ticket-folder}/test-plan-{variation}.md and the acceptance criteria. Read the review notes there too (plan-review-{variation}.md, code-review-{variation}.md, security-review-{variation}.md, test-results-{variation}.md, automated-test-results-{variation}.md, the automated tests' last run, and {ticket-folder}/ci-checks-results-{variation}.md, the project's merge-request CI checks' last run — a check marked ✗ is a gate the merge request's CI would fail, and {ticket-folder}/numbered-files-check-{variation}.md, the numbered files check's last run — each file it names to renumber, and the name to give it): the latest ones say what to fix.
2. Build the planned merge requests one at a time, each after those it depends on. For each:
   a. Have control read them all from the forge: {agent-sh} merge-request:check {project} {ticket} {variation}. Then read them: {agent-sh} ticket:merge-request-plan {project} {ticket} {variation} — each one's id, repository, branch, base, contents, depends-on and status. Skip one Merged or Closed: control decided that, and execution-plan-{variation}.md says why.
   b. In its repository's checkout, git fetch origin, then check out its branch: create it from origin/<base> when it is not there yet; when it is there, rebase it onto origin/<base> and resolve them as Conflicts, below, says. Carry onto it the uncommitted tests and test data the earlier steps left in the checkout (git stash first if the checkout or the rebase refuses, then git stash pop) and commit them there with the code they test.
   c. Implement that merge request's contents from the execution plan, following the patterns already in the repo. Make the automated tests written for the ticket pass; don't weaken or skip them. When you rename or move a test file an entry of {ticket-folder}/automated-tests-{variation}.json names (a renumbered migration or test, say), record that list again with the file's current path, each entry otherwise as it was: `{agent-sh} automated-tests:record {project} {ticket} {variation}`, the whole JSON list on stdin. Commit as you go with clear messages, on that branch alone: never commit to or push its base (main) or any other branch.
   d. Push its branch, even when it holds no changes: git push -u origin <branch> (--force-with-lease after a rebase).
   e. Record it: {agent-sh} merge-request:create {project} {ticket} {variation} <id>. Control opens its draft merge request against its base, or keeps the one open; when the branch has no changes against its base, control marks it Closed instead. Don't open, close or retarget a merge request yourself.
3. Re-check the demo plan against the final change: {agent-sh} ticket:demo-plan {project} {ticket} {variation}. If the change moved anything it pins (pinned commits, refs or expected output), re-record it with `{agent-sh} ticket:set-demo-plan {project} {ticket} {variation}`, the whole JSON on stdin: moving upstream by branch name (e.g. `origin/master`), a commit only for a deliberate "before" state. Otherwise leave it.
4. Append to {ticket-folder}/change-log-{variation}.md (through `{agent-sh} work:append {project} {ticket} {variation} change-log.md`, the entry on stdin): what you built in each merge request, and what deviated from the plan and why.
5. Record each criterion's dev status, <n> its number: `{agent-sh} ticket:set-ac-status {project} {ticket} {variation} dev <n> Passed` for each acceptance criterion your change meets, `{agent-sh} ticket:set-ac-status {project} {ticket} {variation} dev <n> Failed` for one it could not meet.

Conflicts: run `{agent-sh} merge-request:conflicting-tickets {project} {ticket} {variation}` in the conflicted checkout for each ticket whose commits on the base touch the conflicting files — its title, description, acceptance criteria, execution plan and recorded test commands, and the variation it is for; resolve every conflict keeping both changes, and a file it reports "no ticket identified" for from the diff and that file's history, never blocking on it; then, in your own checkout, run this ticket's automated tests and each named ticket's recorded test commands, skipping one that is no longer on the base (exit 127, or it says there is no such test); fix a failure in the files you just resolved, and on any other failure record it with its ticket, push nothing and leave it for a human; append what you resolved, which ticket's change it merged with, the files no ticket was identified for, and the tests skipped or failing, to {ticket-folder}/change-log-{variation}.md (through `{agent-sh} work:append {project} {ticket} {variation} change-log.md`, the entry on stdin).

Numbered files — this project's rule: {numbered-files}. After every rebase, and before every push, re-check each numbered file (a migration, a numbered test) your branch adds against that rule: `{agent-sh} merge-request:check-numbered-files {project} {ticket} {variation}` names each that collides — at or below its target branch's highest, or a number another open merge request opened before yours adds — and the name to give it. Never keep a number because it was free when you chose it. Renumber each it names: git mv it to that name, update every reference to it (code, tests, comments, and an entry of {ticket-folder}/automated-tests-{variation}.json naming it: record that list again, `{agent-sh} automated-tests:record {project} {ticket} {variation}`, the whole JSON list on stdin), commit, and run the check again until it passes. Say what you renumbered, from and to, and why, in {ticket-folder}/change-log-{variation}.md (through `{agent-sh} work:append {project} {ticket} {variation} change-log.md`, the entry on stdin).

If {ticket-folder}/requirements-change-{variation}.md exists, the ticket's requirements changed: read it and revise for the change.
If {ticket-folder}/operator-review-{variation}.md exists, it holds the operator's notes from rejecting earlier passes at Human Review: read it and address each note in this step's work.

Revise, don't restart: if a merge request's branch already holds a solution, revise it — fix what the reviews and test results say, keep what works. Never start it from scratch. Say in change-log-{variation}.md what changed this time, and why.

Don't widen the work beyond the plan and the acceptance criteria.

A golden-image rebuild ticket ("fast-track": true in {ticket-folder}/ticket.json, titled "Rebuild golden-<project>") changes no code and has no merge request: skip step 2. Start the rebuild on the Mac: {agent-sh} vm:build-golden-start <project>, <project> from its title. It starts the ~50-minute build detached and returns at once, its JSON saying the status — don't wait for it: Test checks it. It does nothing while a build runs or once the image is current. Record what it said in change-log-{variation}.md (step 4).

Questions: ask only what the code, the docs, the ticket and {ticket-folder}/questions-and-answers.json can't settle, with `{agent-sh} question:ask {project} {ticket} <--blocking|--non-blocking> "<question>" "<why it is asked>" "<recommended answer>"` — never by writing {ticket-folder}/questions-and-answers.json. --blocking when a wrong guess would cost rework, be irreversible, or is a product or business call only the operator can make: the ticket gets no agent until it is answered, so finish this step without guessing. Else --non-blocking: go on with your recommended answer, recorded as the assumption; an answer that differs comes back as a requirements change.

We want small deliberate changes. You're working with a scalpel, not a broadsword. You're a doctor: get in, fix the root cause using best practices and the patterns already in the repo, get out. Avoid scope creep.
Be extremely concise. Sacrifice grammar for the sake of concision.
