Ticket {ticket}'s requirements changed: the operator took a new description, or answered a question unlike the assumption the work went on. Revise variation {variation}'s acceptance criteria to match it.

1. Read the last "description" line of {ticket-folder}/requirements-history.jsonl (JSON: at, field, from, to): "from" is the old description, "to" the new one. When the file's last line is a "question" one instead (JSON: at, field, question, from, to), the change is that: "from" is the assumption the work went on, "to" the operator's answer to "question"; the description stands.
2. Write {ticket-folder}/requirements-change-{variation}.md (through `{agent-sh} work:write {project} {ticket} {variation} requirements-change.md`, the whole file on stdin): what changed, as "from → to" points, then the new description in full (for a "question" line, the question and its answer). Write it every run, even when nothing has changed: the step goes on only once the file is written.
3. Read the current criteria: the variation's acceptance-criteria in {ticket-folder}/ticket.json. Revise them to the new description: keep a criterion's criteria-number when it still applies (reworded if needed), drop one that no longer applies, give a new one the next unused number. Never renumber the rest.
4. Record them on the variation, [{"criteria-number": 1, "description": "<one outcome a Test agent can check by itself in the ticket's VM>"}, ...] on stdin: `{agent-sh} ticket:set-acceptance-criteria {project} {ticket} {variation} -`. Each criterion is one a Test agent can check by itself in the ticket's VM (commands, tests, the app, screenshots, throwaway data); never one needing the operator, the host, a Claude login, a credential or a live outside system. Where the requirement is only verifiable operator-side, rewrite the criterion as the nearest check an agent can run (e.g. the CLI form against a throwaway store) and leave the operator-side work to the ticket's Operator follow-up section, never a criterion; where no rewrite fits, ask --non-blocking with that rewrite as the recommended answer. Ask with `{agent-sh} question:ask {project} {ticket} <--blocking|--non-blocking> "<question>" "<why it is asked>" "<recommended answer>"` only when no agent-checkable rewrite fits.

Don't judge or change the work: the next step does.
