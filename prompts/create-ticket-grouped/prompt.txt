Headings: H2, in this order:
1. User story: one sentence. "As a <role>, I want <outcome>[, so that <why>]."
2. Context: 1–3 sentences. The root cause and how it produces the symptoms, where (file:line, ticket refs), with its evidence. What is unverified, say so.
3. Acceptance criteria: numbered list. 1–4 testable items. Use "AC1:" prefix or Given/When/Then.

Optional extras: only if real content.
- Scope: between Context and Acceptance criteria. What's in.
- Out of scope: after Acceptance criteria.
- Operator follow-up: after Out of scope. What only the operator, the host, a Claude login, a credential or a live outside system can verify or do. Never a criterion.
- Related: last. Ticket keys plus one-word why.

Rules:
- Same template for Story and Bug.
- No other headings. No Summary, Problem or Goal sections.
- Terse. Fragments OK. No restating the title.
- Criteria are checkable outcomes, not tasks: each says how to see it's done (a command and what it prints, a state), and each is one a Test agent can check by itself in the ticket's VM (commands, tests, the app, screenshots, throwaway data); never one needing the operator, the host, a Claude login, a credential or a live outside system.
- No criterion may need anyone but the operator to touch the operator's uncommitted work or a credential, or to delete or overwrite anything. Work only verifiable operator-side: rewrite the criterion as the nearest check an agent can run (e.g. the CLI form against a throwaway store), else it is Operator follow-up, never a criterion.
- Blocked tickets only as the analysis proves them; nothing guessed.
- Refs: ticket keys, MR !N, repo-relative paths.

Mechanics:
- Where the ticket goes: "Raise the fix ticket in: project <name>" above, when the problem was classified — that project's ticket system, by the work source in {harness-folder}/data/projects/<name>/project.json. Not classified: by where the cause is (cause-in), not where it showed — the project's own code its ticketing system ({project-folder}/project.json), anything else (the harness, the project's environment, the operator's own machine) the harness's off-board system.
- A jira work source: description is ADF JSON with H2 heading nodes and an orderedList for the criteria, written with your Write tool to a temp file (you may write only temp), f.json below; <name> the project's folder under data/projects:
  {harness-folder}/agent.sh ticket:raise-bug <name> "<title>" f.json [Story]   (a Bug unless Story is given)
  It prints {"key": …}: the ticket is assigned to you, in the board's active sprint, at To Do, at the project's bug priority. It exits non-zero naming what is still unset: the ticket exists, so finish with its key. Never raise it through acli directly.
- An off-board work source, or the harness's off-board system: write the same headings as Markdown (H2 sections only, no title line) with your Write tool to a temp file, then:
  {harness-folder}/off-board.sh ticket:create <that project> <Story|Bug> "<title>" <that file>
  It prints the new ticket's key. The ticket starts at Backlog; the harness syncs it onto the dashboard.
- A fix for a blocked ticket whose fix changes what an earlier step of that ticket's engine runs than the step it blocked at (that step's prompt, command or sub-engine — e.g. the plan prompt for a ticket blocked at release): add `--resume-at <that top-level step id>` (plan, build, …) to the off-board create command, so the blocked ticket resumes there and remakes what that step and the ones after it made. Omit it when the fix is to the blocked step itself, or you are unsure.
- Both create commands take the body as a file-path argument, never on stdin: write that file first, in a call of its own (your Write tool, or one Bash call that does nothing else), under a name unique to this run — /tmp/ticket-body-<the title, slugged>.md, say, since another write-ticket run may be staging its own — and name it in the create command by its full path, as you wrote it.
- Run the create command alone, as a bare command line: nothing else on it — no pipe, redirect, heredoc, `&&`, `;`, `$(…)` and no `cd` before it. Anything else runs sandboxed, and the create fails on the ticket store's lock.
- A failed create: report its error, as it printed it, in your final message, then run the same command once more, bare; only if that fails too, finish with an empty key, `no-ticket-reason: create-failed`, and a one-line `why`: the error as it printed.

Finish with JSON: {"key": "<ticket key>", "no-ticket-reason": "<analysis-did-not-hold|create-failed>", "why": "<one line>"} — both "" when a key was created.
