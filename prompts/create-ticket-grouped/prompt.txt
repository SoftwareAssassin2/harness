Before writing, confirm the root cause and evidence still hold (re-run one or two). If the analysis is empty or doesn't hold, write no ticket: finish with an empty key.

Headings: H2, in this order:
1. User story: one sentence. "As a <role>, I want <outcome>[, so that <why>]."
2. Context: 1–3 sentences. The root cause and how it produces the symptoms, where (file:line, ticket refs), with its evidence. What is unverified, say so.
3. Acceptance criteria: numbered list. 1–4 testable items. Use "AC1:" prefix or Given/When/Then.

Optional extras: only if real content.
- Scope: between Context and Acceptance criteria. What's in.
- Out of scope: after Acceptance criteria.
- Related: last. Ticket keys plus one-word why.

Rules:
- Same template for Story and Bug.
- No other headings. No Summary, Problem or Goal sections.
- Terse. Fragments OK. No restating the title.
- Criteria are checkable outcomes, not tasks: each says how to see it's done (a command and what it prints, a state).
- No criterion may need anyone but the operator to touch the operator's uncommitted work or a credential, or to delete or overwrite anything. Work only the operator can do is written as the operator's ("The operator has …").
- Blocked tickets only as the analysis proves them; nothing guessed.
- Refs: ticket keys, MR !N, repo-relative paths.

Mechanics:
- Where the ticket goes: "Raise the fix ticket in: project <name>" above, when the problem was classified — that project's ticket system, by the work source in {harness-folder}/data/projects/<name>/project.json. Not classified: by where the cause is (cause-in), not where it showed — the project's own code its ticketing system ({project-folder}/project.json), anything else (the harness, the project's environment, the operator's own machine) the harness's off-board system.
- A jira work source: description is ADF JSON with H2 heading nodes and an orderedList for the criteria, written to a temp file made with mktemp (you may write only temp), f.json below; <name> the project's folder under data/projects:
  {harness-folder}/agent.sh ticket:raise-bug <name> "<title>" f.json [Story]   (a Bug unless Story is given)
  It prints {"key": …}: the ticket is assigned to you, in the board's active sprint, at To Do, at the project's bug priority. It exits non-zero naming what is still unset: the ticket exists, so finish with its key. Never raise it through acli directly.
- An off-board work source, or the harness's off-board system: write the same headings as Markdown (H2 sections only, no title line) to a temp file, then:
  {harness-folder}/off-board.sh ticket:create <that project> <Story|Bug> "<title>" <that file>
  It prints the new ticket's key. The ticket starts at Backlog; the harness syncs it onto the dashboard.

Finish with JSON: {"key": "<ticket key>"}.
