Extract the acceptance criteria for ticket {ticket} in project {project} into variation {variation}.

1. Read the ticket's description and comments in the ticketing system. Where the ticket has no explicit criteria, derive them from the user story: 1–4 checkable outcomes, not tasks. Each criterion is one a Test agent can check by itself in the ticket's VM (commands, tests, the app, screenshots, throwaway data); never one needing the operator, the host, a Claude login, a credential or a live outside system. Where the requirement is only verifiable operator-side, rewrite the criterion as the nearest check an agent can run (e.g. the CLI form against a throwaway store) and leave the operator-side work to the ticket's Operator follow-up section, never a criterion; where no rewrite fits, ask --non-blocking with that rewrite as the recommended answer.
2. Record them on the variation, a JSON array of objects numbered from 1 — [{"criteria-number": 1, "description": "<one checkable outcome>"}, ...] — on stdin: `{agent-sh} ticket:set-acceptance-criteria {project} {ticket} {variation} -`

Else --non-blocking: go on with your recommended answer, recorded as the assumption; an answer that differs comes back as a requirements change.
